# 재고관리 대시보드

3개 창고(서로 다른 품목군을 관리하는 독립 재고 Pool)에서 매일 추출하는 재고 Excel 스냅샷을 업로드하면
소진 추세·Coverage·예상 소진일·소진 가속/둔화·장기 정체·과잉재고 후보를 계산해 보여주는 사내 재고관리
대시보드입니다. 이 데이터는 **재고 Snapshot이며 판매 데이터가 아닙니다** — 모든 지표는 "추정 소진량",
"관측된 재고 증가"처럼 스냅샷만으로 확인 가능한 사실만 표현합니다.

업로드 캘린더의 **입고 특이사항**에 상품명 또는 상품코드와 실제 입고 수량을 함께 기록하면,
해당 스냅샷 구간의 추정 소진량을 `이전 가용재고 + 입고량 - 현재 가용재고`로 보정합니다.
Excel의 `입고대기` 수량은 실제 입고로 간주하지 않습니다.

재고 Excel은 컬럼 순서나 부가 컬럼과 무관하게 `상품코드`, `상품명`, `정상재고` 헤더만 있으면 업로드할 수
있습니다. `원가`와 `원가합`은 선택이며, 원가가 비어 있으면 동일 SKU의 날짜상 최근 원가를 이어받고
원가합이 비어 있으면 `유효 원가 × 정상재고`로 계산합니다. 그 외 Excel 컬럼은 저장하지 않습니다.

## 기술 스택

- Next.js (App Router) + TypeScript, Tailwind CSS, 수작성 shadcn 스타일 UI 컴포넌트(Radix 기반)
- Recharts, SheetJS(xlsx)
- **Prisma + PostgreSQL** + Auth.js(Credentials, JWT 세션) — Supabase 등 관리형 Postgres의 connection
  string을 `DATABASE_URL`에 그대로 넣으면 배포에도 사용할 수 있습니다.
- Vitest (도메인 계산/Excel 파서 유닛 테스트)

## 로컬 개발 환경 준비

1. PostgreSQL을 준비합니다 (로컬 설치 또는 Docker).
2. `.env.example`을 참고해 `.env`를 작성합니다 (`DATABASE_URL`, `AUTH_SECRET`, `NEXTAUTH_URL`).
3. 의존성 설치 및 마이그레이션:

   ```bash
   npm install
   npm run db:migrate     # 스키마 적용
   npm run db:init        # 창고 A/B/C, 기본 설정값 생성
   npm run db:create-admin -- --email admin@company.com --password admin1234 --name 관리자
   ```

4. (선택) 30/60/90일 이상 데이터가 필요한 기능을 실제 대기 없이 검증하려면 mock 스냅샷 히스토리를 생성합니다.
   실 데이터와는 `isMock` 플래그로 명확히 분리됩니다.

   ```bash
   npm run db:seed              # 이미 있으면 건너뜀
   npm run db:seed -- --force   # 기존 mock을 지우고 재생성
   ```

5. 개발 서버 실행 후 `/login`으로 접속합니다.

   ```bash
   npm run dev
   ```

## 테스트

```bash
npm run test        # 도메인 계산 로직 + Excel 파서/검증/export 유닛 테스트
npx tsc --noEmit     # 타입 체크
npm run build        # 프로덕션 빌드
```

실제 PostgreSQL 통합 테스트와 성능 측정은 별도의 로컬 DB에서 실행합니다. DB 이름은 `_test`로
끝나야 하며, 실행기는 localhost/127.0.0.1/::1 이외의 연결을 거부합니다. `.env`의 운영 URL을
재사용하지 말고 명시적으로 지정하세요. 아래는 PowerShell 예시입니다.

```powershell
$env:DATABASE_URL = 'postgresql://postgres:postgres@127.0.0.1:5432/scm_inventory_test?schema=public'
npx prisma migrate deploy
npm run test:integration
npm run benchmark:inventory
```

DB는 사전에 생성해야 합니다. 테스트는 임의 식별자로 만든 자체 데이터만 정리합니다.
벤치마크 기본값은 500 SKU, 60일 이력, 5회 반복이며 `BENCH_SKUS`, `BENCH_DAYS`,
`BENCH_REPEATS` 환경변수로 변경할 수 있습니다. 측정값은 DB 저장/조회 함수의 실행 시간이며
Excel 파싱, HTTP 전송, 브라우저 렌더링 시간은 포함하지 않습니다.

같은 테스트 DB를 사용하는 앱을 별도 터미널에서 실행한 뒤 `npm run test:smoke`를 실행하면
로그인·Excel 업로드·입고 보정·재업로드·대시보드·리포트 내보내기를 HTTP로 검증합니다.
기본 주소는 `http://127.0.0.1:3107`이며 `SMOKE_BASE_URL`로 로컬 주소를 변경할 수 있습니다.
앱 실행 예: `npm run build` 후 `npm run start -- -H 127.0.0.1 -p 3107`.
앱의 `NEXTAUTH_URL`도 같은 주소로 지정하고 테스트용 `AUTH_SECRET`을 설정하세요.

## 재고·입고·과거 조회의 의미

- 기준일의 SKU 구성은 그 날짜 이전의 최신 ACTIVE 스냅샷으로 결정합니다. 현재 업로드에서
  사라진 SKU도 당시 스냅샷에 있었다면 과거 조회와 과거 일별 합계에 포함합니다.
- 입고 특이사항은 `(이전 관측일, 현재 관측일]` 사이의 수량을 합산하여 소진을 보정합니다.
  스냅샷 없는 날짜의 입고도 반영하며, 과거 스냅샷을 추가하면 구간을 다시 나눕니다.
  첫 관측일 이전·당일의 입고는 비교할 이전 재고가 없어 소진으로 계산하지 않습니다.
- 이벤트의 수량은 메모입니다. 실제 소진 계산을 바꾸려면 업로드 캘린더의 입고 특이사항에
  등록해야 합니다. 일별 입고 합계는 동시 등록을 직렬화하지만 요청 재전송을 자동으로 식별하지는 않습니다.
- 숨김 설정, 수동 위험 기준, 소비기한은 현재 관리 정책이며 과거 조회에도 적용됩니다.
  과거 조회는 보관된 재고를 현재 정책으로 다시 분석하는 기능으로, 당시 화면의 불변 감사 기록은 아닙니다.
- 소비기한은 로트별 날짜를 저장하고 SKU 판단에는 가장 이른 로트 날짜를 사용합니다.
  로트별 잔량과 폐기 예상 수량은 지원하지 않습니다.
- 조회 기준일까지 실제 스냅샷이 존재하는 창고는 mock을 제외합니다. 그 이전 시점을 조회할 때는
  해당 시점의 mock만 사용할 수 있으며, 한 시계열에 mock과 실제 재고를 섞지 않습니다.

업로드는 창고별 잠금과 하나의 트랜잭션으로 스냅샷 버전·현재 SKU 상태를 갱신하고,
SKU와 재고 항목을 1,000행 단위로 저장합니다. 일별 추이는 PostgreSQL에서 원가 이월과
합계를 계산해 집계 결과만 가져옵니다. SKU 분석은 정확한 정체 기간·원가 이월을 위해 아직
전체 관측 이력을 읽으므로, 대규모 데이터에서는 추가적인 분석용 집계 설계가 필요합니다.

## 세그먼트별 입력과 판단 방식

설정 화면은 **공통 / 일일 재고 연동 / 비정기 실사 / 매장 발주 예측** 탭으로 나뉘며, 탭마다 어느 대시보드에 쓰이는 설정인지 표시합니다.

- **비정기 실사**: `/count`에서 센 상품만 직접 입력(상품코드·상품명·재고수량·단위원가·롯트)하거나 `/upload`로 엑셀을 올립니다. 직접 입력은 같은 날짜의 기존 실사에 합쳐지고(부분 실사), 세지 않은 상품을 품절로 보지 않습니다. 상품마다 자기 실사 이력으로 소진 속도와 현재 재고를 추정하며, 실사 권장 주기는 설정에서 바꿉니다.
- **매장 발주 예측**: 발주할 때 수량·지금 남은 양(몇 개 + 열린 것의 %)·충족 매출(이 양으로 감당할 매출)을 적고, 매일 매출만 입력합니다. 남은 매출 여유가 설정의 기준(기본 20%) 또는 리드타임 동안의 매출 아래로 내려가면 "발주 확인 필요"입니다. 재발주가 쌓이면 실제 감당 매출과 실제 사용량(잔량 차이)으로 단위당 매출을 학습해 충족 매출을 보정하고, "입력보다 몇 % 더 팔고 재발주하는지", "재발주 때 보통 얼마나 남는지"를 보여줍니다. 리드타임은 발주처에 지정하면 발주처 값을 씁니다. 충족 매출의 3배 넘게 팔리는 동안 재발주가 없는 품목은 "장기 미발주"로 분리합니다.

## 디렉터리 구조

- `src/domain` — 순수 계산 로직(재고 KPI, Excel 파싱/검증/export). DB·Next.js에 의존하지 않아 유닛 테스트가 쉽습니다.
- `src/server` — Prisma 리포지토리, 서비스 레이어(분석 조립), Auth.js 설정.
- `src/app` — 라우트(페이지, API 핸들러).
- `src/components` — UI. `components/ui`는 shadcn 스타일 프리미티브.
- `prisma/schema.prisma` — 데이터 모델.
- `scripts/` — 운영/개발용 CLI 스크립트(관리자 생성, 초기 데이터, mock 시드).

## 배포 참고

- `DATABASE_URL`을 Supabase(또는 다른 관리형 Postgres) 커넥션 문자열로 바꾸고 `npm run db:migrate`를 실행하면 그대로 배포할 수 있습니다.
- `AUTH_SECRET`은 운영 환경에서 반드시 `openssl rand -base64 32` 등으로 새로 생성하세요.

### 저장 공간 관리

재고 데이터가 쌓일수록 DB 저장 비용이 커지므로 다음처럼 나눠 둡니다.

- **재고 행은 숫자만**: `inventory_items`에는 수량·원가만 저장하고, 상품명·옵션·바코드·위치·파일의 위험/경고수량은 값이 바뀐 날만
  `sku_attribute_versions`에 남깁니다(과거 날짜로 조회하면 그날 효력 있던 값을 씁니다). 같은 날짜를 다시 올리면 이전 버전의 재고 행은 바로 지웁니다.
- **원본 파일은 객체 저장소에**: `FILE_STORAGE_*`(`.env.example` 참고)를 설정하면 업로드 원본 파일을 Cloudflare R2·S3 등에 둡니다.
  이미 DB에 있는 파일은 `npm run db:move-files`로 옮깁니다. 설정하지 않으면 DB에 저장합니다.
- **보관 기한 정리**: 하루 한 번 `/api/cron/maintenance`를 `Authorization: Bearer <CRON_SECRET>` 헤더로 호출하면
  업로드 후 60일이 지난 원본 파일·끝난 업로드 작업 기록(30일)·만료된 토큰과 초대·180일이 지난 운영 기록을 지웁니다. 재고·메모·발주·매출 데이터는 지우지 않습니다.
  Render Cron Job, GitHub Actions `schedule`, cron-job.org 같은 외부 스케줄러를 쓰거나 서버에서 `npm run db:maintenance`를 실행하세요.

### Render로 배포하기

저장소 루트의 `render.yaml`이 웹 서비스(`baskit-web`)와 PostgreSQL(`baskit-db`)을 함께 선언하는 Blueprint입니다.
기존 사내용 서비스(`scm-inventory-*`)와 이름이 겹치지 않아, 같은 Render 워크스페이스에 만들어도 서로 영향이 없습니다.

1. Render 대시보드 → **New** → **Blueprint** → `Baskit-Project` 저장소 연결.
   Blueprint 파일은 **`claude/intelligent-mayer-ilfo5t` 브랜치**에 있으니 브랜치를 반드시 이것으로 선택하세요
   (`main`에는 아직 초기 커밋만 있습니다).
2. Render가 `baskit-db`와 `baskit-web`을 함께 생성합니다. `DATABASE_URL`은 자동 연결되고 `AUTH_SECRET`은 자동 생성됩니다.
3. 생성 화면(또는 웹 서비스 Environment)에서 `NEXTAUTH_URL`을 배포 URL(예: `https://baskit-web.onrender.com`)로 채웁니다.
4. 첫 배포가 끝나면 `/signup`에서 워크스페이스와 첫 관리자를 만들면 됩니다. 별도 초기화 스크립트는 필요 없습니다.
   (카페 데모 데이터가 필요하면 Render Shell에서 `npm run db:seed-store -- --org-id <워크스페이스 id>`)

주의:
- `baskit-db`는 유료 `basic-256mb`(0.1 CPU · 256MB)로 운영합니다. DB 요금제는 대시보드가 아니라 `render.yaml`의 `plan`에서 바꾸세요 —
  둘이 다르면 Blueprint 동기화가 실패하거나(예: "cannot downgrade database … to Free") 요금제가 되돌아갈 수 있습니다.
- 가입(`/signup`)은 누구나 호출할 수 있습니다. 공개 전에 요청 횟수 제한·이메일 인증을 추가하세요.

### 운영자 콘솔 (`/admin`)

가입한 워크스페이스 현황·제어(정지, 관리 방식 변경, 사용자 비활성화·임시 비밀번호, 삭제), 워크스페이스
"들어가기"(해당 워크스페이스 화면을 관리자 권한으로 그대로 확인), 세그먼트별 데모 워크스페이스 생성을 제공합니다.
모든 조치는 운영 기록(감사 로그)에 남습니다.

운영자 권한은 가입 이메일로 판단하지 않고 DB 값(`users.isPlatformAdmin`)으로만 판단하며, 앱 화면에서는 줄 수 없습니다.
(가입에 이메일 인증이 없어 이메일만 보면 그 주소로 먼저 가입한 사람이 권한을 가져갈 수 있기 때문입니다.)

1. 배포된 사이트의 `/signup`에서 본인 워크스페이스·계정을 만듭니다.
2. Render DB 화면의 **External Database URL**을 복사해 로컬에서 실행합니다(무료 플랜은 Shell이 없음):

   ```bash
   DATABASE_URL="<External Database URL>" npm run db:grant-platform-admin -- --email me@example.com
   ```

3. 다시 로그인하면 사이드바에 **운영자 콘솔**이 보입니다. 권한 회수는 같은 명령에 `--revoke`를 붙입니다.

재배포 시 `startCommand`의 `prisma migrate deploy`가 스키마 변경을 자동 적용합니다.


## 스냅샷 기반 핵심 KPI (2026-09-18)

핵심 KPI를 재고 보유 SKU 비율, 무재고/음수재고 SKU, 평가 가능한 금액과 평가 범위,
기준일 미관측 SKU로 교체했습니다. 현재 업로드가 보존하는 정상재고가 수량 기준입니다.
각 창고의 기준일 이전 최신 ACTIVE 스냅샷에 존재하며 숨김 처리되지 않은 SKU만 포함합니다.
따라서 상품 마스터 전체의 가용성이나 주문 충족률을 뜻하지 않습니다.

- 보유율 = 정상재고 > 0인 SKU 수 / 조회 대상 SKU 수. 데이터가 없으면 산정 불가입니다.
- 금액은 업로드 원가합 우선, 없으면 유효 원가 × 정상재고입니다. 원가 이력이 없는 재고는
  명시적인 0원과 구별해 제외합니다. 음수재고/음수금액도 제외하고 평가 범위를 표시합니다.
- 기준일 미관측은 마지막 관측일이 조회 기준일보다 이전인 SKU입니다. 하루 차이도 표시하며,
  현재 재고가 확인됐다고 가정하지 않습니다. 창고별 날짜가 다르면 가장 오래된 관측일도 표시합니다.
- 기간 비교는 양 끝 날짜가 정확히 관측된 동일 SKU만 포함합니다. 신규 SKU, 날짜 누락,
  0일 구간은 직전 관측 증감으로 대체하지 않습니다. 음수재고 경계값도 비교에서 제외합니다.
- 순감소/순증가는 SKU별 양 끝 재고 차이를 집계합니다. 구간별 입고 보정 추정 소진은
  max(이전 재고 + 기록된 입고 - 현재 재고, 0)의 합입니다. 두 수치는 의미가 다릅니다.
- 품절 추정/커버리지는 마지막 관측일 기준 동일한 7/14/30일 창을 사용하며 실제 관측 구간
  합계가 최소 7일이어야 합니다. 7일·14일 비교는 각각 7일, 과잉 후보는 30일 관측을 요구합니다.
  관측 근거 수준은 예측 정확도의 확률이 아니며 HIGH를 부여하지 않습니다.

화면과 전체 Excel 리포트는 동일한 순수 계산 함수를 사용합니다. DB 스키마 변경은 없습니다.
판매·출고·반품·조정의 완전한 원장, 매출원가, 로트별 잔량이 없어 재고회전율·DIO·GMROI·
주문 충족률·로트별 폐기량은 구현하지 않습니다. 상세 추정값은 보조 판단 자료입니다.


## 2026-09-19 운영 지표 기준

상품을 소싱해 판매하는 운영에 맞춰 일반 판매 SKU와 일괄 납품 B2B를 구분합니다.
입력은 상품코드·상품명·원가·재고, 선택적 입고 기록 및 로트별 소비기한입니다.
주말과 설정에 등록된 공휴일에는 출고가 없습니다. 기준일 마감 재고를 같은 시점에 관측한다는
가정으로 이전 기준일 다음 날부터 현재 기준일까지의 출고 영업일을 셉니다.

| 지표 | 산식·표시 기준 |
|---|---|
| 직전 관측 대비 | 현재 재고 − 직전 관측 재고. 판매량이 아님 |
| 최근 7일 추정 소진 | 관측일 기준 최근 7달력일 안에 완전히 들어오는 구간별 max(이전 재고 + 기록 입고 − 현재 재고, 0) 합계. 경계에 걸친 구간은 임의 배분하지 않음 |
| 출고일평균(7일) | 위 합계 ÷ 포함된 구간의 실제 출고 영업일 수. 관측 일수 병기, 자료 없음과 0소진 구분 |
| 커버리지 | 관측 재고 ÷ 선택된 창의 출고일평균 추정 소진. 단위는 출고일 |
| 산출 근거 선택 | 최근 7/14/30달력일 중 5출고일 이상·3구간 이상·최대 구간 3출고일 이하를 만족하는 가장 짧은 창 |
| 예상 소진일 | 마지막 관측일에 ceil(커버리지) 출고일을 더함. 주말·등록 공휴일 건너뜀. 2,600출고일 초과는 날짜 산출 보류 |
| 변화율 | 최근 7달력일 출고일평균 ÷ 직전 7달력일 출고일평균 − 1. 두 창 모두 해당 출고일 전체 관측·각 3구간 이상일 때만 표시 |
| 무소진 출고일 | 마지막 추정 소진 관측부터 마지막 재고 관측까지 출고일 수. 재고 입고일/실제 보관기간은 아님 |
| 과잉 후보 | 일반 SKU 중 30달력일 창에 15출고일·10구간 이상이 있고 미설명 증가가 없을 때, 해당 평균으로 계산한 커버리지를 수동 설정 기준과 비교 |
| 소비기한 확인 | 양수 재고에서 최단 로트 소비기한−안전 여유 달력일이 지났거나, 예상 소진 날짜가 그 날짜보다 뒤면 확인 표시. B2B·예측 불가 품목은 임박 날짜만 확인 |
| 원가·재고금액 | 현재 관측 재고의 평가 가능한 금액. 원가 미상은 0원과 구분 |

일수 설정(stockoutSoonDays/manageMaxDays/overstockCoverageDays/stagnantDays)의 **기존 숫자는 유지하되
단위를 출고일로 해석**합니다. 소비기한 여유 일수(expirationRiskDays)는 계속 달력일입니다.
예를 들어 커버리지 10출고일은 공휴일이 없으면 약 2주입니다. 설정 화면에서 운영 기준을 확인하세요.

추정치를 사용할 수 없는 신규/희소 이력, 미설명 재고 증가, 음수재고, 평일 자료 누락은 판단
보류 사유를 표시합니다. 반품·조정을 구분하지 못하므로 충분한 이력이 있어도 정확한 판매량이나
예측 확률을 의미하지 않습니다. 소진율 0은 무한 커버리지/정상으로 처리하지 않습니다.

B2B는 현재 관측 재고금액과 소비기한 확인 대상에 포함하지만 커버리지·소진일·가속·정체·과잉
자동 판단에서는 제외합니다. 발주 확정 수량과 납품 예정일이 없어 전량을 예약 재고라고 단정하지 않습니다.

최신 업로드 목록에서 사라진 SKU는 운영 정책에 따라 **품절**로 분류합니다.
1개월간 이력 확인용으로 남기고 현재 재고금액·보유율
집계에서 제외합니다. 목록과 엑셀의 현재 수량·금액은 0으로 표시하며 상세에는 마지막 관측값을 보존합니다.
목록 이탈을 가상의 출고 이력으로 만들지는 않습니다. 다시 나타나면 새 관측 이력으로 분석합니다.

로트별 수량이 없으므로 폐기 예상량·FEFO 차감·소비기한 위험 금액은 산출하지 않습니다. 리드타임,
판매가, 반품·조정 원장이 없어 자동 발주점/발주량·안전재고·GMROI·마진도 산출하지 않습니다.
공휴일은 설정에 등록된 날짜만 적용되며 자동 수집하지 않습니다.
